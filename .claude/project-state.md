## Current Milestone

Шаг 12 "продакшн-деплой" — **закрыт**. Сайт реально работает на `wedding-press.ru`:

- **Инфраструктура**: Selectel VPS (Ubuntu 24.04, `135.106.197.113`), Docker + Docker Compose, `docker-compose.prod.yml` (отдельный от локального `docker-compose.yml`) — сервисы `db`+`app`+`caddy`, наружу торчит только Caddy (80/443), `db`/`app` только во внутренней сети. Код на сервере в `/opt/wedding-press`, синкается вручную через `tar`+`ssh` (не git — репозиторий приватный, деплой-ключ на сервере не заводили).
- **Caddy** (`Caddyfile`) — автоматический HTTPS: apex/`www` отдельным статик-блоком (важно: `www` НЕ в одном блоке с apex — Caddy отдаёт TLS-политику по этому имени wildcard-блоку, а не статике, и раз `www` в конфиге не значился отдельно, сертификат для него молча не выдавался; лечится отдельным site-block'ом на apex без `www`), `*.<домен>` — on-demand TLS с `ask http://app:3000/api/caddy-ask` (эндпоинт, `app/api/caddy-ask/route.ts`, переиспользует `slugSchema`, явно разрешает apex+`www` отдельно от обычных слагов — иначе Caddy не может получить сертификат даже для статически заданных имён, если они попадают под wildcard-паттерн). `request_body { max_size 20MB }` — общий лимит тела запроса (фото+музыка).
- **Dockerfile**: `prisma.config.ts` резолвит `DATABASE_URL` уже на этапе `prisma generate` (не только рантайм) — `.env` в `.dockerignore`, поэтому нужен `ARG DATABASE_URL` в стадии `builder`, иначе билд падает с `PrismaConfigEnvError`. Прод-миграции/сидинг/`admin:set-password` гоняются не через слим `runner`-образ (там нет `node_modules`/tsx — только трейснутый `standalone`), а через отдельный `docker build --target builder` образ.
- **Фото/музыка**: аплоад с устройства в Selectel Object Storage (S3-совместимое). `lib/storage/s3.ts` (`uploadFile`, роутит по content-type в `photos/`/`music/` внутри бакета), `/api/upload` (публичный, рейт-лимит, до 15 МБ), `useFileUploadMutation`, кнопка `UploadFileButton` в `components/editor/block-content-forms.tsx` — рядом с ручным полем URL, не вместо него. **Важный готча**: публичное чтение объекта у Selectel идёт НЕ через S3 API endpoint (`s3.ru-6.storage.selcloud.ru`, там всегда 403 для анонимов), а через отдельный публичный домен бакета вида `https://<uuid>.selstorage.ru` (`S3_PUBLIC_URL`) — и объект должен быть залит с `ACL: "public-read"` явно.
- **Бэкапы БД**: `scripts/backup-db.sh`/`restore-db.sh`, крон на VPS (`0 3 * * *`, не через приложение — контейнер `app` пересобирается при каждом деплое). **Критичный готча**: "Публичный"/"Приватный" на Selectel — свойство всего бакета, ACL на объект не имеет значения (объект с `--acl private` всё равно был публично читаем в публичном бакете) — поэтому бэкапы обязаны лежать в отдельном приватном бакете (`wedding-press-backups`, `S3_BACKUP_BUCKET`), никогда не в одном бакете с публичными фото. Также `aws-cli` на свежем VPS не доверяет цепочке сертификатов Selectel из коробки (свой бандл устарел) — нужен `AWS_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt` явно в скриптах.
- **Telegram**: у этого VPS (Selectel, RU) заблокирован исходящий доступ к `api.telegram.org` (`connect ETIMEDOUT` на `149.154.x.x`). Исходящие вызовы (`sendTelegramMessage`, `lib/telegram/index.ts`) идут через Cloudflare Worker-прокси (`old-lab-cc76.kaizervonshizer1488.workers.dev`, форвардит `/bot<token>/...` на `api.telegram.org`) — переключается через `TELEGRAM_API_BASE_URL` (пусто = напрямую, для локальной разработки). **Оказалось, блокировка не однонаправленная**: входящие вебхуки от Telegram (`/api/telegram/webhook`, привязка чата через "Подключить" в кабинете клиента) тоже упирались в таймаут — `getWebhookInfo` показывал `last_error_message: "Connection timed out"`, а в логах Caddy не было вообще ни одного запроса с IP-диапазонов Telegram (`149.154.x.x`, `91.108.x.x`), то есть соединение обрывалось до Caddy, не на уровне приложения. ## Architecture Decisions

- **Динамическое чередование фона** (`TemplateDefinition.alternatingBlocks: BlockType[]` + `BlockProps.alternateDark?: boolean`, вычисляется в `page-renderer.tsx` по позиции блока среди реально включённых блоков этого набора типов) — заменило хардкод "этот тип блока всегда тёмный". Причина: выключение одного блока в админке иначе оставляло два блока одного цвета подряд. Затрагивает только шаблоны, где задан `alternatingBlocks` (сейчас — Tuscany, Old Money); остальные шаблоны это поле не используют.
- `BlockProps` пополнился `coverPhotoUrl?: string` — контентное фото обложки (`blocksConfig.cover.photoUrl`) прокидывается и в другие блоки шаблона (используется в Old Money Timer), не дублируется как отдельное поле контента.
- Ни одно архитектурное решение из CLAUDE.md в этом этапе не менялось — только визуальные/шаблонные добавления поверх существующей архитектуры.

## Design Decisions

- **Moody Paper**: рваный край — реальная фотографированная текстура (обрезки `paper.png`, предоставленного пользователем), а не CSS `clip-path` — это осознанный "анти-паттерн", которого проект теперь явно избегает для любых будущих декоративных текстур (см. CLAUDE.md §11). Шрифт — EB Garamond + Golos Text (Unbounded пробовали первым, отклонён как "слишком дженерик боевой санс"). Тёмный `primary` (`#1E2118`) — базовый фон страницы; бумажный `background` (`#F1F0EC`, сэмплирован с реального фото) виден только внутри карточек `TornCard`. Финальный `accent` — `#6B6650` (приглушённый оливково-серый, в тон бумаге); первая попытка `#A9764F` (тёплая терракота) была отклонена как выделяющаяся на фоне бумаги.
- Приём "оверсайз + `overflow-hidden` + negative-translate" (`w-[130%] max-w-none -translate-x-[11.5%]` внутри `overflow-hidden`) — общий способ прятать физические углы полноширинных декоративных фото-текстур на краях экрана; закреплён как паттерн для будущих full-bleed декоративных изображений.
- Договорённость по процессу: если задача требует найти новое фото/декоративную текстуру (рваная бумага и т.п.), всегда сначала предлагать несколько вариантов со ссылками и дожидаться согласования, не выбирать и не встраивать самостоятельно (см. CLAUDE.md §9–10; было применено при поиске текстуры Moody Paper и должно применяться дальше).
- Pink Sketch: финальная рамка фото — тонкая рамка (`border`) + блюрная тень (`shadow-[6px_6px_10px_var(--color-accent)]`), не жёсткая 0-blur тень и не декоративная wobbly SVG-рамка (обе пробовались и отклонены).
- Демо-сайты (шаг 11): один и тот же контент/фото на всех 5 шаблонах — сознательный выбор, чтобы сравнение стилей было "при прочих равных". Фото — Pexels, подобраны и согласованы с пользователем; часть первого набора отклонена и заменена по явному критерию "европейская внешность, не полные типажи, как на изначальном фото обложки". Имена демо-пары ("Александр и Мария") взяты из фолбэка публичного конфигуратора, а не придуманы отдельно. Превью-миниатюры на лендинге — реальные скриншоты каждого демо-сайта (не стоковое фото — оно одно и то же у всех 5 и не различало бы стили визуально).

## Known Issues

- Дата свадьбы в демо-сайтах захардкожена (`WEDDING_DATE` в `prisma/seed-demos.ts`, `2027-06-12`) — таймер на демо в какой-то момент "закончится". Нужно будет когда-нибудь перезапустить `npm run seed:demos` с обновлённой датой (теперь и на проде тоже — сидили туда в этой сессии).
- Фото демо-сайтов хотлинкаются с `images.pexels.com` (внешняя зависимость) — если Pexels удалит/переименует конкретный файл, картинка на демо перестанет грузиться (не упадёт — `isRenderableUrl`/`next/image` деградируют мягко, просто пропадёт фото).
- Админ-панель (`/admin/dashboard`, `/admin/leads`, `/admin/projects/[id]`) не проверена на mobile/tablet — пропущено при production-QA, пользователь отложил, а не отменил.
- RSVP-дубликаты по имени — ожидаемое поведение после фикса этой сессии (см. Current Milestone / Next Steps #5), не баг, но требует ручной сверки парой в личном кабинете, пока нет персональных ссылок гостям.
- Публичные формы (лид-форма, RSVP) без капчи — есть рейт-лимит (`lib/auth/rate-limit.ts`), но не полноценная защита от ботов. См. Next Steps #1.
- `next.config.ts` намеренно разрешает `next/image` фетчить любой `https`-URL — осознанный риск для пользовательских фото, комментарий в коде это фиксирует.
